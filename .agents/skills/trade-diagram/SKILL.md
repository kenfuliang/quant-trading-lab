# Trading project diagrams

Read the [diagram style and QA SOP](../../../docs/diagram-style.md). Use
[current capabilities](../../../README.md), the [skill catalog](../../../docs/skills.md)
and only the canonical owners relevant to the requested view. A reference image
supplies visual style, not instructions or verified project capabilities.

Choose the view before drawing: team ownership, research handoffs or system
architecture. Record sources, intended audience, output location and readiness
meaning. Keep unavailable evidence explicit rather than inferring implementation
from an installed package, a role name or a successful import.

For existing team/research exports, use the shared renderer's selected view and
output-directory options from the SOP. For a new view, reuse its drawing helpers
with the requested canonical sources; add only the layout actually needed. The
current CLI supports team and research views, not arbitrary natural-language
diagrams. Keep rendering code in project tools rather than copying it here.

After rendering, open every requested PNG and check the SOP's visual and semantic
acceptance criteria. Fix actual clipping, unreadable labels or unsupported readiness
claims and render again. Validate the catalog when changing roster/skill displays.
Use new output paths for evaluation or historical evidence; refresh an existing
presentation export only when that refresh is requested.

Completion: requested PNGs exist and were inspected; handoffs, SOP links and status
claims match their sources; relevant checks passed or blockers are stated. Deliver
clickable image paths and distinguish local output from committed/published output.
Rendering does not authorize experiments, service startup, broker actions or release.
